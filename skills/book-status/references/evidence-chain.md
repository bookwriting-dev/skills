# Evidence that a scene depends on

Review the actual prose for claims that change what a character can do, know, prove, or carry forward. Use the existing [continuity review](continuity-review.md) record and its source hashes. Work from exact passages. Search the manuscript by event, artifact, or quoted words when the relevant chapter is outside the recent packet.

1. Identify the assertion, who makes it, and whether the prose treats it as established, suspected, reported, or intentionally false. Separate a character's stated belief from the narrative's warrant for it. Check a callback against the actual earlier event or transcript. Preserve a marked lie, a supported deduction, and a question the story deliberately leaves open.
2. Name the same object, event, revision, and processing stage on both sides before comparing. A separate authorization, converted copy, new bundle, or changed custodian can account for a difference when the manuscript establishes it. Trace each decisive object or payload from its source through the relevant handoff. Record custody changes with the existing state operation and cite the action on the page.
3. Use the typed claims below for comparisons the runtime can repeat. For a consequential conclusion that needs judgment, record a support assessment and the passages that justify it. Distinguish what a source establishes from what the later claim adds. A label can establish the printed date. A conclusion about when a recording was made needs evidence about the recording history. An estimate, forecast, or promise becomes a firm constraint only when the text establishes it as one.
4. For a real-world premise that determines whether the outcome is possible, inspect a primary source or appropriate expert material. Verify the specific assertion and its scope, record the edition or revision and limitations, and retain the exact passage or locator. Use the [assertion evidence contract](../../nonfiction-research/SKILL.md#assertion-evidence-readiness) on the affected chapter, scoped to its load-bearing real-world claims. Apply fictional setting rules from the book Wiki or the manuscript as story evidence. When evidence is missing, record the assertion as unresolved with the question to resolve.
5. Run the continuity audit again after recording the claims. Inspect the passages behind each finding. Carry the returned input paths into saved chapter checks. Confirmed contradictions and load-bearing support findings block a clean chapter gate. A missing anchor or unresolved unit conversion is a comparison note until the passages establish a conflict. Submission and publication preflight also recheck current evidence and include its dependencies.

## Additional claim kinds

All claims still require the chapter's exact line and quote. Specify only source-backed facts. Keys refer to entities or named events in this book.

| Kind | Additional fields |
|---|---|
| Date | Use kind `date`, event `key`, and a complete ISO calendar date as `value`. A printed or alleged date can have its own key. |
| Calendar span | Use `year_span` with date keys `start` and `end` and an integer `value` for completed calendar years. Supply a precise on-page date or established canon on both ends. |
| Clock and duration | Existing `clock` and `duration` values default to minutes. Set `unit` to `seconds` for second precision. Clock values share an origin, including day offsets. Set `minimum: true` when an operation takes at least that long within the named interval. Tolerance uses the same unit as the claimed duration. |
| Exclusion window | Use `exclusion` with `clock`, `start`, `end`, and `event` keys when the text expressly rules out an event between two inclusive clock anchors. A different person's visit, an estimate, or a different route may need its own event key. |
| Attribute | Use `attribute` with artifact `key`, `stage`, `attribute`, and `value`. Give numeric values a `unit`. The check normalizes Hz, kHz, and MHz and warns on other unmatched units. Record sample rate and bandwidth as different attributes. Use distinct stages only when the sources establish the distinction. |
| Bundle | Use `bundle` with package `key`, revision `snapshot`, `members` as an array of stable item keys, and `complete` as a boolean. A partial description asserts only the listed contents. The runtime checks each assertion against a complete inventory for that revision when available. |
| Support | Use `support` with claim `key`, `basis` (`story` or `research`), `assessment` (`supported`, `contradiction`, or `unresolved`), a `rationale`, and `references`. Each reference gives `path`, one-based `line`, exact `quote`, and `source_sha256`. A supported story claim and a contradiction both need an independent passage. The project-relative path may point to established prose or project canon. |

For a supported research assertion, add `research: {"path": "...", "sha256": "...", "assertion_id": "..."}` to its support claim. The referenced `chapter_evidence` record must be eligible under the shared evidence contract, identify the same chapter revision, and verify the exact assertion span. Use matching quotes in both records. Store a retained source snapshot with its digest where available and permitted. The continuity audit tracks the research record and local snapshots as dependencies. When only an edition and passage locator are available, the evidence documents the reviewer's inspection of that version. The runtime checks the evidence record and retained files. Source interpretation and inventory coverage remain editorial work.

## Drafting from earlier evidence

Put the referenced claim, object, and event keys on the scene plan's `Continuity keys:` line. Verify cited facts and inspect any support findings carried in the draft packet. If the scene uses a source whose support is missing or has changed, reopen the question before writing a consequential conclusion. Keep the evidence in production context and keep blind reading packets restricted to the reader's text.
